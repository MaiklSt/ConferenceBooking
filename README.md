# Conference Booking API

API для управління конференц-залами, бронюваннями та розрахунком вартості оренди.

Компанія здає зали в оренду бізнесу. Через API клієнт може знайти вільний зал, забронювати його разом із послугами та одразу побачити підсумкову ціну. Для компанії є звіти: завантаженість залів, виручка та популярні послуги.

## Бізнес-завдання

- Додавати, змінювати та видаляти конференц-зали.
- Шукати вільні зали за датою, часом і місткістю.
- Бронювати зал з обраними послугами.
- Рахувати вартість оренди залежно від години доби.
- Бачити аналітику для бізнесу.

### Початкові дані

| Зал | Місткість | Базова ціна, грн/год |
|-----|-----------|----------------------|
| Зал A | 50 | 2000 |
| Зал B | 100 | 3500 |
| Зал C | 30 | 1500 |

Послуги в кожному залі:

| Послуга | Ціна, грн |
|---------|-----------|
| Проєктор | 500 |
| Wi-Fi | 300 |
| Звук | 700 |

### Тарифи за часом

Робочі години: **06:00–23:00**. Бронювання не може вийти за цей інтервал.

| Період | Години | Коефіцієнт |
|--------|--------|------------|
| Ранок | 06:00–09:00 | −10% |
| Стандарт | 09:00–18:00 | базова ціна |
| Пік | 12:00–14:00 | +15% (має пріоритет над стандартом) |
| Вечір | 18:00–23:00 | −20% |

Ціна залу рахується похвилинно: кожна хвилина бере коефіцієнт свого періоду. Послуги додаються один раз за бронювання.

Приклад: Зал A, 10:00–14:00, послуга «Проєктор»:

- 10:00–12:00 — 2 год × 2000 = 4000
- 12:00–14:00 — 2 год × 2000 × 1.15 = 4600
- Проєктор — 500
- **Разом: 9100 грн**

## Технічне рішення

Clean Architecture з чотирма проєктами. Залежності спрямовані всередину: зовнішні шари знають про внутрішні, Domain не залежить ні від чого.

```
HTTP-запит
    ↓
API              контролери, Swagger, валідація, обробка помилок
    ↓
Application      сценарії: зали, бронювання, звіти
    ↓
Domain           Room, Booking, Service, розрахунок ціни
    ↓
Infrastructure   in-memory сховище та seed-дані
```

| Проєкт | Відповідальність |
|--------|------------------|
| `ConferenceBooking.Domain` | Сутності та бізнес-правила (ціна, перетин бронювань, робочі години) |
| `ConferenceBooking.Application` | Use cases, DTO, інтерфейси репозиторіїв, FluentValidation |
| `ConferenceBooking.Infrastructure` | Реалізація сховища. Зараз — пам'ять; пізніше можна замінити на EF Core + SQL без зміни Application |
| `ConferenceBooking.API` | HTTP, Swagger, middleware помилок |

Чому так:

- **Масштабованість** — сховище і API можна міняти окремо.
- **Чистота** — бізнес-логіка не змішана з HTTP і БД.
- **Відмовостійкість** — помилки ловляться в одному місці, клієнт отримує зрозумілий JSON, без stack trace.
- **Безпека входу** — некоректні дані відсікаються валідацією до бізнес-логіки.

Дані живуть у пам'яті, поки працює застосунок. Після перезапуску знову підставляються зали A/B/C.

## API

Базовий URL: `http://localhost:5102`

| Метод | Шлях | Опис |
|-------|------|------|
| `GET` | `/api/rooms` | Усі зали (щоб взяти ID залу та послуг) |
| `POST` | `/api/rooms` | Створити зал |
| `PUT` | `/api/rooms/{id}` | Оновити зал |
| `DELETE` | `/api/rooms/{id}` | Видалити зал (якщо немає бронювань) |
| `GET` | `/api/rooms/available` | Вільні зали за часом і місткістю |
| `POST` | `/api/bookings` | Забронювати зал і отримати вартість |
| `GET` | `/api/reports/summary` | Зведення: завантаженість, виручка, послуги |
| `GET` | `/api/reports/occupancy` | Завантаженість залів, % |
| `GET` | `/api/reports/revenue` | Виручка по залах |
| `GET` | `/api/reports/services` | Популярні послуги |

### Створити зал

```http
POST /api/rooms
Content-Type: application/json

{
  "name": "Зал D",
  "capacity": 40,
  "baseHourlyRate": 1800,
  "services": [
    { "name": "Проєктор", "price": 500 },
    { "name": "Wi-Fi", "price": 300 }
  ]
}
```

### Знайти вільні зали

```http
GET /api/rooms/available?startTime=2024-09-01T10:00:00&endTime=2024-09-01T14:00:00&minCapacity=50
```

Для 50 осіб повернуться Зал A і Зал B. Зал C (30 місць) не потрапить у список.

### Забронювати

Спочатку `GET /api/rooms`, скопіюй `id` залу і `id` послуги.

`duration` у форматі `гг:хх:сс`.

```http
POST /api/bookings
Content-Type: application/json

{
  "roomId": "підстав-id-залу",
  "startTime": "2024-09-01T10:00:00",
  "duration": "04:00:00",
  "selectedServiceIds": ["підстав-id-послуги"]
}
```

Відповідь містить `totalCost`. Повторний пошук на цей самий слот уже не покаже зайнятий зал.

### Звіти

Завантаженість рахується від робочих годин **06:00–23:00** (17 год на день). Бронь 10:00–14:00 за один день — близько 23.53%.

```http
GET /api/reports/summary?from=2024-09-01T00:00:00&to=2024-09-02T00:00:00
```

## Помилки

Усі помилки у форматі:

```json
{
  "status": 400,
  "error": "Запит не пройшов валідацію.",
  "details": ["Назва залу є обов'язковою."]
}
```

| Код | Коли |
|-----|------|
| 400 | Некоректні дані або порушення бізнес-правила |
| 404 | Зал не знайдено |
| 500 | Неочікувана помилка (без внутрішніх деталей) |

## Що далі (масштабування)

- Замінити in-memory сховище на EF Core + PostgreSQL/SQL Server через ті самі `IRoomRepository` / `IBookingRepository`.
- Додати автентифікацію (JWT) і ролі: адміністратор залів / клієнт бронювань.
- Ідемпотентність і блокування слота при одночасних бронюваннях.
- Персистентні логи та health-check для продакшену.
